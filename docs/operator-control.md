# Центральная панель Smart Leads

Панель запускается как отдельный сервис со своей PostgreSQL, доменом и ключом входа. Клиенты остаются на VPS оператора в отдельных контейнерах и базах. Парсер и существующий вход клиентов не меняются.

## Название переменной подключения

В **каждом отдельном клиентском приложении Smart Leads** в Coolify добавьте:

```dotenv
SMART_LEADS_INSTANCE_KEY=
SMART_LEADS_CONTROL_URL=https://control.example.ru
```

После создания карточки центральная панель выдаст полный ключ `slk_...`. Вставьте его в `SMART_LEADS_INSTANCE_KEY`. ID уже содержится внутри ключа, отдельная переменная ID не нужна. Пока создаёте шаблон, можно оставить обе переменные пустыми: отправка отчётов выключена. Если заполнить только адрес, агент сообщит о неполной конфигурации и останется выключенным.

`SMART_LEADS_CONTROL_URL` — один HTTPS-адрес админской панели Smart Leads Control для всех клиентов; замените пример своим доменом. В клиентском приложении откройте **Environment Variables → + Add**. В окне **New Environment Variable** введите **Name** и **Value** для первой переменной, затем так же добавьте вторую. Внизу окна для каждой переменной выберите **Build time**: недоступна при сборке (вместо `Available during build`); **Runtime**: `Available in the container`; **Value type**: `Single line`. Это выпадающие списки, а не переключатели. Нажмите **Add Variable**, затем выполните **Redeploy** клиентского приложения. [Документация Coolify](https://coolify.io/docs/applications/configuration/environment-variables).

Не используйте `NEXT_PUBLIC_` для ключей. Ключ подключения не заменяет `DATABASE_URL`, ключи сессий, шифрования, `CRON_SECRET` или токены интеграций.

## Развёртывание центрального сайта

Центральный сайт — **Smart Leads Control**, админская панель из репозитория `SMART_LEADS_CONTROL`, например `https://control.example.ru`. Продаваемое приложение **Smart Leads** — другой сайт: для каждого клиента он запускается отдельно на его VPS со своей базой, например `https://client.example.ru`. В проекте и окружении Coolify (`SMART_LEADS_CONTROL` → `production`) находятся два ресурса: приложение админской панели и её PostgreSQL.

1. Откройте в Coolify **Проекты → SMART_LEADS_CONTROL → production**. Если приложение центрального сайта уже есть в списке ресурсов, создавать его повторно не нужно.
2. В этом же окружении нажмите **+ Новый ресурс → PostgreSQL** и выберите тот же сервер и назначение, что у приложения. Coolify предложит имя ресурса, пользователя, пароль и начальную базу. Автоматическое имя менять не требуется. Значения `postgres` для пользователя и начальной базы допустимы; пароль оставьте сгенерированным. Поле **Сопоставление портов / Ports Mappings** оставьте пустым: если там стоит `3000:5432`, удалите эту запись. Порт `3000` нужен приложению сайта, а PostgreSQL доступна ему по внутреннему порту `5432`. Не включайте **Открытый доступ / Make it publicly available**. Сохраните ресурс и нажмите **Start / Запустить**; дождитесь рабочего состояния. Если PostgreSQL уже создана, используйте существующий ресурс, очистите сопоставление портов, сохраните и проверьте её состояние.
3. Откройте ресурс PostgreSQL → **Общая информация** и скопируйте целиком поле **URL Postgres (внутренний)** / **Internal URL**. Coolify формирует его из пользователя, пароля, внутреннего имени контейнера, порта `5432` и имени базы: `postgresql://USER:PASSWORD@HOST:5432/DB`. Вручную собирать URL и заменять `HOST` на IP VPS не нужно. Не публикуйте URL: в нём есть пароль.
4. Откройте ресурс **приложения центрального сайта** в том же окружении. Если его ещё нет, создайте приложение из репозитория `SMART_LEADS_CONTROL` со способом сборки **Dockerfile**: Base Directory — `/`, Dockerfile Location — `/Dockerfile.operator`. Укажите Ports Exposes `3000`, свой HTTPS-домен и проверку здоровья `/api/health`. [Пути Dockerfile в Coolify](https://coolify.io/docs/applications/builds/dockerfile).

   Если после смены Railpack на Dockerfile деплой стал красным и журнал пишет `open Dockerfile: no such file or directory`, откройте **Настройки → Общие → Сборка** этого же приложения. Coolify ищет стандартный `Dockerfile`, которого здесь нет. Оставьте **Base Directory** `/`, в **Dockerfile Location** впишите `/Dockerfile.operator`, сохраните настройки и повторите **Deploy**. Не меняйте путь на `operator/`: инструкция сборки лежит в корне репозитория и сама копирует папку `operator`.

5. В приложении откройте **Environment Variables / Переменные окружения** и добавьте три серверные переменные. Для каждой включите **Runtime Variable** и выключите **Build Variable**:

| Переменная | Что вставить |
| --- | --- |
| `OPERATOR_DATABASE_URL` | Полный **URL Postgres (внутренний)**, скопированный из ресурса PostgreSQL на шаге 3 |
| `OPERATOR_PUBLIC_URL` | Внешний адрес панели, например `https://control.example.ru`, без пути и параметров |
| `OPERATOR_ADMIN_KEY` | Случайный секрет не короче 32 символов, общий ключ входа оператора |

Генерация нового ключа входа на своём компьютере или VPS:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

6. Сохраните переменные и выполните **Deploy / Redeploy** приложения. Дождитесь рабочего состояния. Панель сама создаст таблицы `operator_instance` и `operator_audit`; вручную открывать SQL-консоль и выполнять миграции не требуется.
7. Проверьте `https://ВАШ-ДОМЕН/api/health`, затем откройте корень HTTPS-домена и войдите с `OPERATOR_ADMIN_KEY`. Этот ключ не передаётся клиентам. Сессия действует восемь часов. Смена ключа и повторный Deploy аннулируют старые сессии; обычный перезапуск с тем же ключом их не сбрасывает. Если приложение не запускается, проверьте его логи, состояние PostgreSQL и значение `OPERATOR_DATABASE_URL`.

Образ центрального сервиса использует Node.js 22 и `pg`, работает от пользователя `node`. Сборка Next.js, Python и MAX-парсер центральному сервису не нужны.

## Где остаются данные после перезапуска

**Не добавляйте том на экране «Постоянное хранилище» приложения Smart Leads Control только потому, что список пуст.** Панель не пишет реестр в файлы контейнера: карточки клиентов, последний отчёт и журнал действий находятся в её отдельной PostgreSQL. Coolify при создании отдельного ресурса PostgreSQL автоматически подключает к нему постоянный том. Откройте **ресурс PostgreSQL → Постоянное хранилище** и убедитесь, что том есть. У PostgreSQL 18 каталог данных внутри контейнера — `/var/lib/postgresql`; не создавайте второй том с другим путём поверх существующего. `OPERATOR_ADMIN_KEY` и две другие переменные панели остаются в настройках Coolify после перезапуска; храните отдельную защищённую копию секретов.

У **каждого клиентского Smart Leads** свои приложение, PostgreSQL, секреты и файловый том. Настройки одной установки не следует переносить в центральную базу Control:

| Что нужно сохранить | Где хранится | Что настроить в Coolify |
| --- | --- | --- |
| Пользователи и права, добавленные чаты и источники, материалы, настройки клиента и интеграций | PostgreSQL **этого клиента** | Отдельный ресурс PostgreSQL с постоянным томом; его Internal URL — в `DATABASE_URL` и `DIRECT_URL` клиентского приложения |
| Вход первоначального администратора клиента | Его числовой MAX ID или Telegram ID — в `ADMIN_MAX_IDS` / `ADMIN_TELEGRAM_IDS`; профиль и связанные данные — в PostgreSQL клиента | Настроить хотя бы один действующий способ входа: MAX-бот + `ADMIN_MAX_IDS` либо Telegram Login + `ADMIN_TELEGRAM_IDS`; ключи и ID задаются в клиентском приложении, не в Control |
| Аккаунт MAX, который читает чаты для парсера | Запись и зашифрованная резервная копия сессии — в PostgreSQL клиента; рабочий JSON-файл сессии — в `/app/data/sessions` | В клиентском приложении задать постоянные `PARSER_PROXY_ENCRYPTION_KEY`, `PARSER_SESSION_ENCRYPTION_KEY`, `PARSER_SESSIONS_DIR=/app/data/sessions` и подключить том к `/app/data`. Сам аккаунт авторизовать через QR в админке клиента |
| Ключ входа в панель Control | Переменная `OPERATOR_ADMIN_KEY` ресурса **центрального приложения** | Сохранить в Coolify и в защищённом хранилище оператора; не вводить его в клиентское приложение |

Порядок для **нового клиентского экземпляра**, а не для уже созданного приложения Smart Leads Control:

1. В Coolify создайте проект/окружение клиента, отдельную PostgreSQL и приложение из репозитория клиентского Smart Leads. Убедитесь, что в **PostgreSQL → Постоянное хранилище** уже есть созданный Coolify том. Скопируйте **URL Postgres (внутренний)** этой базы; не берите URL базы Control.
2. В **клиентском приложении → Постоянное хранилище → + Добавить монтирование → Монтирование тома** заполните **Имя** (например, `smart-leads-data`), **Исходный путь / Source Path** оставьте пустым (если показан пример `/root`, удалите его), **Целевой путь / Destination Path** укажите `/app/data`. Нажмите **Добавить том** и выполните Redeploy. Так файлы в `/app/data/sessions` останутся после пересоздания контейнера. Если клиент уже работал без тома и создал файлы сессий, сначала сохраните и перенесите их: новый пустой том не восстановит файлы старого контейнера. [Тома Coolify](https://coolify.io/docs/core/persistent-storage/storage-mounts/volume-mounts).
3. В **Переменные среды** клиентского приложения задайте `DATABASE_URL` и `DIRECT_URL` из Internal URL его PostgreSQL (без пулера могут совпадать), `NEXT_PUBLIC_APP_URL` с HTTPS-доменом клиента, `AUTH_SESSION_SECRET`, `CRON_SECRET`, `PARSER_PROXY_ENCRYPTION_KEY`, `PARSER_SESSION_ENCRYPTION_KEY` — разные постоянные случайные секреты от 32 символов — и `PARSER_SESSIONS_DIR=/app/data/sessions`. При первом входе также задайте один рабочий способ авторизации: `ADMIN_MAX_IDS` и данные MAX-бота либо `ADMIN_TELEGRAM_IDS`, `TELEGRAM_CLIENT_ID`, `TELEGRAM_CLIENT_SECRET`. Подробности и остальные интеграции — в [инструкции владельца клиентского приложения](https://github.com/a77446446-ctrl/Smart-Leads/blob/main/docs/owner-setup.md). Секреты нужны **во время выполнения** контейнера; для секретов отключите доступность во время сборки.
4. После первого входа в **админке самого клиента** подключите MAX-аккаунт парсера через QR и добавьте нужные чаты/источники. Аккаунт парсера не вводится в переменные Control. В панели Control создайте карточку клиента и добавьте выданные `SMART_LEADS_CONTROL_URL` и `SMART_LEADS_INSTANCE_KEY` в переменные **клиентского** приложения, затем выполните Redeploy.
5. Настройте резервные копии **обеих PostgreSQL** и клиентского тома `/app/data` с копией вне VPS. Том обеспечивает сохранение при пересоздании контейнера, но сам по себе не заменяет резервную копию. После Redeploy проверьте вход администратора клиента, список чатов и активность MAX-аккаунта. Смену ключей шифрования без переноса старых данных не выполняйте: сохранённые сессии и настройки могут перестать читаться.

## Подключение нового клиента

1. Нажмите **Создать экземпляр**. Заполните название, клиента, HTTPS-домен и условия обслуживания.
2. Скопируйте показанный блок из двух переменных. Секрет показывается один раз, в базе хранится только SHA-256. Закройте окно после сохранения ключа.
3. Создайте клиентское приложение в Coolify обычным способом: собственная PostgreSQL, домен, секреты и постоянные тома. Создание карточки само по себе не создаёт VPS или контейнер.
4. Вставьте блок подключения в Environment Variables этого приложения и выполните Redeploy.
5. Клиентское `npm start` запускает независимый агент мониторинга. Первая отправка — примерно через 15 секунд после запуска агента, последующие — через пять минут после предыдущей попытки. В режиме `npm run dev` агент не запускается автоматически.
6. Дождитесь статуса **На связи** в реестре. Список обновляется автоматически раз в минуту; можно нажать **Обновить**.
7. Внутри самого клиентского приложения заполните интеграции по [памятке владельца](https://github.com/a77446446-ctrl/Smart-Leads/blob/main/docs/owner-setup.md).

Необязательная переменная `SMART_LEADS_APP_VERSION` задаёт метку релиза для карточки. Без неё отправляется версия из корневого `package.json`.

## Отчёты и их смысл

Пользователь явно согласовал следующий состав отчёта:

- версия приложения;
- число неудалённых материалов и пользователей;
- число доставок MAX в состояниях `PENDING`, `RETRY`, `PROCESSING`;
- число доставок MAX в состоянии `FAILED`;
- размер PostgreSQL через `pg_database_size`;
- максимальное `lastSuccessAt` аккаунтов парсера.

Тексты, телефоны, имена читателей, токены интеграций и MAX-сессии не передаются. Для отчётов используется исходящее HTTPS-соединение клиента с отдельным ключом. Перенаправления запрещены, сетевой запрос ограничен десятью секундами. Центральный сайт не подключается к клиентской PostgreSQL. Агент читает только агрегаты, использует одно соединение в режиме read-only и ограничивает время SQL десятью секундами.

| Статус | Значение |
| --- | --- |
| Ожидает подключения | Ключ выпущен, отчёта ещё не было |
| На связи | Центр получил отчёт не более 15 минут назад |
| Нет свежих данных | Последний отчёт старше 15 минут; состояние приложения неизвестно |
| Ключ отозван | Приём отчётов выключен оператором |

«На связи» не означает, что работают все интеграции. Проверяйте отдельно время успешного сбора и очередь. Время последнего отчёта устанавливает сервер при приёме. Хранится только последний отчёт; графиков истории нет. Отчёт содержит очередь MAX, Telegram-доставка не отслеживается. Недоступность центра не останавливает приложение: агент повторит попытку через пять минут.

## Короткие инструкции менеджеру

**Ключ потерян:** открыть карточку → Выпустить новый ключ → вставить новый блок в Coolify клиента → Redeploy. Старый ключ перестаёт работать сразу. Если окно с ключом закрыто до копирования, снова выпустите ключ.

**Нужно отключить мониторинг:** карточка → Отозвать ключ. Приложение продолжает работу. Для восстановления связи выпустите новый ключ.

**Оплата обслуживания:** после подтверждения оплаты заполните «Оплачено по». Эта дата включает весь день по Москве. Стоимость задаётся в рублях в месяц и хранится в целых копейках. Изменение периода и стоимости видно в журнале. Здесь учитывается обслуживание экземпляра, отдельно от покупок лидов внутри клиента; автоматических списаний и выставления счетов нет.

**Пауза / архив:** изменить статус в карточке. Это статус учёта, не команда остановки контейнера и не удаление данных. Для реальной остановки используйте свой Coolify.

**Резервная копия:** настройте копирование PostgreSQL и клиентских файлов средствами инфраструктуры. После успешного выполнения вручную укажите дату копии. Поле «Проверка восстановления» заполняйте только после фактического восстановления на отдельном тестовом окружении. Сами копии панель не создаёт. Отдельно резервируйте базу центрального реестра.

**Нет отчёта:** проверить обе переменные и Runtime-флаг → Redeploy клиента → проверить DNS, HTTPS центра и `/api/health` → найти `[МОНИТОРИНГ]` в логах клиентского приложения → при отозванном ключе выпустить новый. Не публиковать ключи и строки подключения в обращениях поддержки.

**Карточка изменена в другом окне:** закрыть её, обновить список и открыть снова. Проверка `revision` защищает от незаметной перезаписи; ротация ключа и изменения карточки сохраняются вместе с журналом в транзакции.

## Локальный запуск

После установки зависимостей `npm ci` в каталоге `operator` задайте `OPERATOR_DATABASE_URL`, `OPERATOR_PUBLIC_URL` и `OPERATOR_ADMIN_KEY`. Затем запустите из корня репозитория `node operator/server.mjs`. Для локальной разработки разрешён адрес `http://127.0.0.1:3200` при `NODE_ENV=development` и `PORT=3200`; на VPS используйте HTTPS и `NODE_ENV=production`. `file:///.../index.html` не подходит: интерфейсу нужен сервер API.

## Проверки и границы версии

Центральный Docker-образ устанавливает зависимости по `operator/package-lock.json`. Для ручной проверки выполните `npm ci` в каталоге `operator`, а затем запустите сервис и проверьте `GET /api/health`. Интеграционные тесты центральной панели и клиента находятся в [репозитории Smart-Leads](https://github.com/a77446446-ctrl/Smart-Leads). В этой версии реализованы реестр, ключи, мониторинг, ручной учёт обслуживания, отметки копий, аудит и встроенные инструкции. Автоматическое создание ресурсов Coolify, обновление / остановка клиентских контейнеров, автоматический биллинг, управление копиями и персональные роли сотрудников требуют отдельных этапов. Используется один доступ оператора, поэтому журнал не различает нескольких сотрудников с одним ключом.
